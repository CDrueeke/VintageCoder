# PRALLBALL (MEGA65)

Port of the C64 game `examples/c64/prallball` to the MEGA65 (no shared code with the C64, the source is copied and adapted).
Rules, levels, extras and controls as on the C64 (joystick port 2 or keyboard: Z left, X right, space fire).

- **Build:** `vcc build .` (or IDE F7), start in Xemu (`xmega65 -prg build/prallball.prg -prgmode 65`, in the IDE F5).
  Test version in which the computer plays: `vcc asm prallball.asm --target mega65 --cpu 45gs02 -D AUTOPLAY=1 -o autoplay.prg`.
- **Structure of the source:** the header of `prallball.asm` contains the flow, memory map (CPU RAM, chip RAM, palette, zero page), units and the list of all
  test versions (`-D ...`); every routine has a header comment with input/output.  The following points describe the development stages and functions.
- **State (stages 2a, 2b and 2c; basis, later extended to full color characters and 640 x 400, see below):** the game began in the VIC-II mode of the VIC-IV (40 x 25 multicolor text, 8 sprites) and uses its **VIC-IV palette**:
  16 own colors (`pal_r/g/b`) and a **soft background gradient** instead of 22 color bands: 50 bands of 4 raster lines each set
  palette entry 0 (background and border) to color values from `lib/gradient.inc` (4 gradients, generated by `tools/gen_gradient.py`).
- **Sound (stage 2b), four SIDs:** SID 1 the title music as on the C64, SID 2 a detuned chorus of the same voices (+0.6 %), SID 3 octave doubling
  (melody and arpeggio +12 semitones as triangle, bass -12 as pulse), SID 4 the sound effects layered in three voices (main tone, octave above,
  noise for brick, hard brick and loss). The music is thus never interrupted by effects. Only started in Xemu, the SID registers cannot be
  read back: **not listened to, only the program run checked**. Library: `examples/mega65/prallball/lib/sound.asm`.
- **16-color sprites (stage 2c):** ball (sprites 3, 4, 5) and paddle (sprites 1, 2) are VIC-IV sprites in full color mode (16 pixels wide,
  4 bits per pixel, `$D06B`): a shaded ball with a highlight (blue, golden on piercing by switching the sprite palette) and a
  metallic shaded paddle with round ends. The sprites have their own palette bank (`$D070`, bank 1, entry sprite * 16 + color value);
  color value 0 is transparent. The wide paddle (48 px) uses an X-doubled second sprite. The **capsule** (sprite 0) is a shaded 16-color coin with a dark letter;
  the palette (entries 0-15 of the sprite bank) is switched per capsule kind (`set_cap_pal`), the rotation phases are four coin images. The **laser shots**
  (sprites 6 and 7) are 16-color sprites (white/yellow). So all eight sprites are in 16-color mode.
  The data is generated by `tools/gen_sprites16.py` into `lib/sprites16.inc` (from `$B000`). Seen in Xemu: ball, paddle (32 and 48 px), golden ball (test version `-D TESTWIDE=1`).
- **High score list on the device (file `PRALL.HS`):** at start `hs_load_kernal` loads the list while the KERNAL is still visible (before `mega_init`); at the
  game end `hs_save` writes it: `hs_env_in` restores the state of SYS (`$01`/`$D030` from the program start, raster interrupt of the VIC off, `map` with
  A = $00, X = $00, Y = $00, Z = $83 = block `$E000` onto the KERNAL; at the idle prompt of BASIC the monitor shows MAPL = $E300 / MAPH = $B300, but this does not hold for
  a SYS program: with this mapping the code at `$2000` was hidden), `hs_env_out` restores the game environment and calls `hs_after` (= `vic_init`, the
  graphics chip registers may have changed). Measured in Xemu (device 8 = host directory "XEMU EXTERNAL"): (1) `SETBNK(0,0)`, `SETMSG(0)`; (2) `LOAD` and
  `SAVE` via `SETNAM`/`SETLFS`/`SAVE` hung, sequential files (`OPEN 2,8,2,"PRALL.HS,P,W"`, `CHKOUT`, `CHROUT`, `CLRCHN`, `CLOSE`, `CLALL`) work cleanly; (3) an
  `OPEN` for writing to an existing file hangs (even with `@0:`): the old file is deleted beforehand through the command channel (`OPEN 15,8,15,"S:PRALL.HS"`);
  (4) the DMA audio samples must not be in `$10000-$107FF` and `$11800-$11FFF` (the DOS of the KERNAL works there): now `$10800-$117FF`, `$1C800`, `$1F000`.
  Checked in Xemu: loading, saving, loading again in the running game (test version `-D TESTHS=1 -D TESTHS_A=1`, results from `$7000`), the list is kept across several
  program runs; the real game end (name entry with auto-confirmation, `hs_insert`, `hs_save`) was also run through in Xemu with the test version `-D TESTLOSE=1` (score 500 preset); at the next start the title screen shows the saved entries. **Not** checked on a real MEGA65.
- **Palette animation (MEGA65 only):** (1) the blue ball gradually turns red with speed (steps 4-7, 8-11, 12-15; tables `heat_r/g/b`, generated by
  `tools/gen_sprites16.py`; `set_ball_pal` writes the sprite palette).  (2) The border flash (ball lost, hit, core) fades out softly: palette color
  `FLASHPAL` ($FB) is darkened by a quarter per frame (`flash`, `flash_fade`).  (3) During name entry the border pulses yellow.  Test version
  `-D TESTSPEED=n` starts with step n.
- **Debris particles (MEGA65 only):** every destroyed brick sprays 4 splinters in its color (up to 8 at the same time, `particle_*` in `prallball.asm`). A splinter
  is a full color character (8 x 8, pixel value 255 = color from color RAM) with a 2 x 2 or 3 x 3 spot in one of the four quarters; the 8 characters are located from
  `$1CE00` (character number `$738`) and are cleared with the **DMA controller** (fill job, format F018A) and then filled with dots.  They fly with
  gravity over empty cells (they are invisible in front of bricks, wall and text; a spot always replaces a whole cell, over a brick it would make half of it
  disappear) and work in 320 x 200 and 640 x 400.  Test versions: `-D CRUMBTEST=1` (8 bricks at once), `-D PTFREEZE=n` (freeze the picture
  as soon as a splinter has only n frames left to live).  Seen in Xemu.
- **Wandering bricks (MEGA65 only):** occasionally (on average about every second, if there is a free neighbor cell) a brick (type 1-10, not in bonus
  and boss levels) comes loose and glides softly by one position to the left, right, up or down (0.4 s); at most 2 at the same time (`MAXW`, `wander_*` in `prallball.asm`).
  Drawing: the brick pattern (full color character) is placed shifted by 0..7 pixels into a character strip in chip RAM (cleared beforehand by DMA) and the
  strip is written to the screen within the two cells; works in 320 x 200 and 640 x 400.  The strip memory is unused in the respective other
  mode ($14800 or $12000); therefore switching (`toggle_mode`) regenerates the brick data of the new mode (`fcm_init` / `hires_init`) and
  `toggle_game` stops wandering bricks at their source beforehand (`wander_settle`).  **Collision by visible position:** during the movement the brick is not entered
  anywhere in the map; ball (`wcoll`, in both axes of `move_ball`) and laser shots (`wshot`) check against its position in playfield points.  A
  hit brick stays at the nearest cell and is treated like any brick (points, splinters, break).  A wandering brick waits if the
  ball is in the way.  Test versions: `-D WTEST=1` (frequent, counts hits/ends in `wdbg`), `-D WTEST2=1` (always bricks in row 9), `-D WTEST3=1` (bricks stop
  in the middle of the movement), `-D WFREEZE=n` (freeze the picture at progress n/16 point), `-D WVERT`/`WHORZ`/`WUP` (direction), `-D TESTTOG=1` (switch every 256 frames
  ).  Seen in Xemu (both resolutions, all directions, switching in the game); hits on wandering bricks counted with `WTEST3`.  Speed,
  frequency and number are not yet tuned in the game.
- **Stereo position (MEGA65 only):** the DMA samples (brick, hard brick, core, laser) sound where they happen: `sfx_pan` (0 left .. 255 right, center 128) sets
  the left/right volumes of DMA channel 0 (`$D729`/`$D71C`); `hit_brick` takes the column of the brick, the laser the paddle position. The registers were read in
  Xemu through the monitor (values change with the brick), it was not listened to.
- **DMA audio and 40 MHz (stage 2e):** the processor runs at 40.5 MHz (`$D031` FAST and `$D054` VFAST; the FAST bit in `$D031` must be set because
  every write to `$D011`/`$D016`/`$D018` sets it again from `$D031`). The game logic is frame-bound and runs unchanged (AUTOPLAY delivers the same
  values as at 1 MHz). The **audio DMA** (`$D711 = $80`, channel 0, `$D720-$D72F`) plays digital samples in addition to the SID effects: crack (brick), tone
  (hard brick), bang (loss), ping (extra), zap (laser). The samples are **generated in the program at start** (noise, pulses, low pass, triangle,
  falling tone; 8 bit signed, 6 kHz) and are located in chip RAM bank 1 (`$10800-$117FF`, `$1C800`, `$1F000`; `dma_init`/`dma_play` in `examples/mega65/prallball/lib/sound.asm`). Checked in Xemu:
  the sample data (contents and decay per page) and that the channel runs to the end (`CHxSTP` set, address at the end); **not listened to**.
  Test version `-D TESTDMA=1` plays the bang at start.
- **Polyphonic music:** the player (`examples/mega65/prallball/lib/sound.asm`) reads two songs of the same format: track 1 (melody, bass, drums/arpeggio) plays on
  SID 1 and detuned as a chorus on SID 2, track 2 (`mus_init3`: counter voice in diatonic thirds, echo, two chord tones) on SID 3. `tools/compose.py` generates
  both (`song`, `song3` in `lib/music.inc`, from `$E000`). Without `mus_init3` SID 3 plays the octave doubling as before.
- **Full color graphics (FCM, super extended attribute mode):** `seam_regs` switches the VIC-IV to 16-bit character numbers (`$D054` = `$45`): every text cell has 2 bytes
  of screen (now at `$C800`, 25 * 80 bytes) and 2 bytes of color RAM (access via the 32-bit pointer `cq` to `$FF80000`, byte 1 = color). Hot registers
  (`$D011`, `$D016`, `$D018`, `$D031`, `$DD00`) reset this setting; the raster interrupt therefore calls `seam_regs` after every write to `$D016` and `$D011`.
  Character numbers from 256 are full color characters: data at number * 64 in chip RAM (`FCM_BASE` = `$480`, i.e. `$12000`), 8 bits per pixel, pixel value = palette index.
  The bricks (24 types and the white highlight version) have rounded corners, light and shadow edges, highlight stripes and 8 brightness steps per type (palette
  32 to 223); wall (steel with rivet) and logo block (solid border, area with pixel value 255 = color from color RAM) as well. `tools/gen_bricks.py` generates only
  ONE brick pattern; `fcm_init` builds the 24 types from it in chip RAM at start (add the palette range per type). Data: `lib/bricks.inc` from `$E900`
  (do not use `$F700-$FFFF`: the C65 system writes there).
- **Break animation:** a destroyed brick flashes white (type 24), crumbles in two phases (`crumble_pat`: 2 x 2 large pieces that fall by a few rows) and disappears; up to 8 at the same time (`crumble_start`, `crumble_tick`, `crumble_reset`). Test versions: `-D CRUMBSLOW=1` (phase 1 stays 5 s) and
  `-D CRUMBTEST=1` (destroys 8 bricks of row 3 after 100 frames); seen in Xemu.
- **Switchable resolution (key R, on the title and in the game):** the game runs in 320 x 200 or 640 x 400 (`$D031`: bit 7 H640 and bit 3 V400). The game logic
  always calculates in 40 x 25 logical cells; only the screen build-up differs (`hires` = 0/1, `mode_set`, `toggle_mode`, `toggle_game`). **320 x 200:** as before.
  **640 x 400:** a logical cell is 2 x 2 characters (80 x 50 cells of 8 x 8 pixels, 160 bytes per row). The bricks (32 x 16 pixels, 4 x 2 full color characters)
  have rounded corners, light edge, highlight bands, highlight spot and an ordered dither between the 8 palette steps; wall (steel with rivet) and logo block are 16 x 16
  pixels in size; the font is created at start from the 8 x 8 character set (each character from four full color characters, `hires_init`), enlarged and smoothed with the EPX method (Scale2x, `font_epx`): diagonals are soft instead of stair-stepped; ticker and scroller are
  8 x 8 characters of the high resolution (half as big, but finer). Bricks come in 10 color groups with three versions each (brick, break 1, break 2; `tools/gen_bricks.py`,
  `brick_grp` assigns a group to every type). **Sprites in 640 x 400** (`tools/gen_sprites640.py`, `lib/sprites640.inc` from `$8000`, `spr_mode`, `update_sprites_h`): `SPRH640` (`$D054` bit 4) and `SPRENV400` (`$D076`) make a sprite point
  a real pixel, a 16-color sprite is 16 points wide, the height is in `$D055`/`$D056` (16 rows; the blocks are 128 bytes in size). Coordinates: X' = x + 79 (10 bits: `$D010` bit 8, `$D05F` bit 9),
  Y' = y + 107 (9 bits: `$D077` bit 8). Ball 12 x 12, paddle 12 rows high (narrow: left + right; normal: left, center X-doubled, right = 64 points; wide: all three doubled = 96 points; if
  sprite 7 is occupied by a shot, two doubled ends remain), coin 16 x 16 with letter, shot 4 x 16; sprite 7 is the third paddle part when no shot needs it; the palette of
  sprites 6 and 7 contains in 640 x 400 the paddle ramp and shot colors (`set_s67_pal`). When switching, `spr_mode` sets pointers, height, doubling and palette. The raster gradient counts real
  screen lines in the high resolution: the interrupt line is 2 * T (9 bits, bit 8 in `$D011` bit 7 set only on change because `$D011` is a hot register), the scroller is moved finely in band 49. The screen (8192 bytes) is in chip RAM at `$1D000` and is written through the 32-bit pointer `sq` (in the 64 KB space it would overflow `$D000`),
  the font from `$18800`, the bricks of the high resolution from `$14800`. Start in 640 x 400 for tests: `-D START_HIRES=1`. Seen in Xemu (title and game, both
  directions of switching). **Not yet:** the sprites were only seen in Xemu (ball, paddle in three widths, capsule, shots, title balls); the position is matched to the character grid to about one pixel, not against real hardware.
- **Not yet:** high score list checked on a real MEGA65.
- **Memory (MEGA65 deviations):** program from `$2001` (BASIC 65 start); the code is longer than fits between `$0801` and `$3FFF`, therefore
  VIC bank 2 is used (`$8000-$BFFF`): sprite pointers `$87F8`, character set `$8800`, sprites `$9000`, levels `$9400`, 16-color sprites `$B000`; brick map `$C000`,
  title music `$E000`, full color data `$E900`; screen in chip RAM `$1D000` (see above).
  Start (`mega_init`): `map` cancels the BASIC 65 banking, `$01 = $35` (RAM up to `$FFFF`, I/O at `$D000`), unlock the VIC-IV
  (`$D02F`), 40 columns; interrupt vector in RAM (`$FFFE`), the interrupt saves the registers itself. The character set comes from the
  chip ROM (`$2D000`, via a 32-bit pointer).
- **Tests:** `python3 tools/gen_tests.py` generates `prallball.vctest` (trap at `$1F00`). The 8 static checks pass (segment sizes and positions,
  cycles of `add_score`). The trap tests (`vcc test --backend xemu`) now run and no longer hang, but deliver unreliable results (8 of 63 passed,
  some subroutines do not return and the emulator is restarted): the test jumps into the routine in the state of the BASIC 65 start (C65 banking, ROM at `$E000`, zero page
  and interrupt of the system) without `mega_init` having run; e.g. `rand_byte` returns `$43` instead of `$CB` from `$A5/$5A`, `add_score` leaves the digits
  unchanged. A solution needs a setup step in the test runner (start the program and stop only after `mega_init`) or a trap after the initialization; it lies
  in the test runner (`crates/vc-emu`), not in the game. The AUTOPLAY version serves as a functional test (in Xemu the computer plays, also in both resolutions).
- **Libraries:** `examples/mega65/prallball/lib/input.asm`, `hiscore.asm`, `rand.asm`, `sound.asm` (copies of the C64 version).

## Settings and demo player (new)

At the beginning of `prallball.asm` is the **EINSTELLUNGEN** block (can also be set with `-D NAME=value` when assembling):
`EXTRA_RATE` (40: chance in 256 per destroyed brick for capsules; about twice as many as before), `DEMO_REAKTION_MIN`/`DEMO_REAKTION_MAX` (4/12 frames of reaction time after a change of direction of the ball), `DEMO_FEHLER_RATE`, `DEMO_FEHLER_FERN`, `DEMO_UNGENAU`, `DEMO_VERFEHLEN_RATE`, `DEMO_EXTRA_LUST`, `DEMO_EXTRA_FERN`.
The demo player thus seems more human (reaction time, short mistakes, inaccurate hits, rare deliberate misses) and catches good falling capsules as long as the ball is far away.
Test version `-D AUTOPLAY=1 -D TESTDEMO=1` counts events of the demo player in RAM (see the header comment).

**Angle randomness (new):** On each paddle hit the bounce angle is shifted by exactly one zone (17 degrees) to the left or right with the chance `WINKEL_ZUFALL` (default 64 of 256, about every fourth hit). This applies to the human player and to the demo player; the ball always stays within the eight zones, and at the edges it is not pushed beyond them. It prevents endless, identical ball paths. `0` switches it off (`-D WINKEL_ZUFALL=0`). With `-D AUTOPLAY=1` the computer now plays all levels without end (before: only the first five); `-D TESTDEMO=1` additionally counts the angle shifts, the paddle hits, the completed levels, the destroyed bricks and the levels ended by the time limit (addresses in the header of `prallball.asm`).

**Demo time limit (new):** If the demo player hits no brick for `DEMO_STEIN_LIMIT` seconds (default 40), the level counts as completed and the next one begins, so an unreachable or tough last brick cannot hold the demo up endlessly. Only in the demo (and with `AUTOPLAY`), never in the game for humans; `0` switches it off.
