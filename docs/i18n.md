# Mehrsprachigkeit (i18n) für Entwickler

Stand: Etappe I2 (Meldungen umgestellt). Maßgeblich ist das Konzept `assets/docs/Konzept-Mehrsprachigkeit-i18n.md`; hier steht, wie man mit dem Gerüst arbeitet.

## Grundsätze

- **Deutsch ist die Quelle und der Rückfall.** Fehlt ein Schlüssel im Englischen, erscheint der deutsche Text; fehlt er auch dort, steht ein sichtbarer Hinweis da (`⟦schlüssel⟧` im Debug-Bau, `{schlüssel}` im Release) und das Debug-Protokoll bekommt einmal einen Eintrag. Es gibt nie einen Absturz.
- Sprachen: `de`, `en` und die **Pseudo-Sprache `xx`** (nur zum Prüfen). Eine fremde Systemsprache ergibt Englisch.
- Kataloge sind Fluent-Dateien (`.ftl`) unter `crates/vc-i18n/catalog/de/` und `catalog/en/`, nach Bereichen getrennt (`gui.ftl`, `settings.ftl`, `assistants.ftl`, …) und **in die Programmdatei eingebettet** (`include_str!` in `crates/vc-i18n/src/lib.rs`, Liste `CATALOGS`).
- **Maschinenlesbares wird nie übersetzt**: Fehlercodes, Dateiformate, JSON-Schlüssel, Direktiven, Schlüsselwörter, Menükennungen im Code (`"Datei"` ist die Kennung, `befehle::menue_titel("Datei")` der angezeigte Titel).
- Feste Wörter: „Zeropage“ bleibt im Deutschen unübersetzt, im Englischen heißt es „zero page“ (in Zusammensetzungen „zero-page addressing“). „Onion Skin“ bleibt in beiden Sprachen so. `tools/check_schreibweise.py` prüft das je Sprache.

## Regel G9: keine neuen festen Texte im Code

Ab jetzt steht **jeder neue sichtbare Text im Katalog** und wird mit `t!` geholt. Feste deutsche Zeichenketten in den Anzeige-Crates (`vc-gui`, `vc-gui-ui`, `vc-ide-model` und die Anzeigemodule von `vc-ide`) meldet `tools/check_i18n.py` als Fehler; technische Fälle (Dateinamen, Vergleichsmuster, Ausgabedateien) stehen mit Begründung in `tools/i18n_ausnahmen.txt`. Die Oberfläche ist seit Etappe I1 umgestellt.

## Einen Text hinzufügen

1. Schlüssel nach dem Schema `<bereich>-<ort>-<zweck>` wählen, klein, mit Bindestrichen: `menu-file`, `status-tree-summary`, `settings-language-title`. Schlüssel werden **nie umbenannt**; Veraltetes bekommt die Zeile `# veraltet seit 0.4.0` darüber und wird später entfernt.
2. Den Eintrag in **beide** Dateien schreiben (`catalog/de/<bereich>.ftl`, `catalog/en/<bereich>.ftl`); ein Kommentar über dem Eintrag erklärt den Zusammenhang für die Übersetzung (`# Kontext: n = Zahl der Dateien`).
3. Im Code: `vc_i18n::t!("schlüssel")` oder mit benannten Parametern `vc_i18n::t!("schlüssel", n = 3, name = datei)`. Parameter dürfen Zahlen oder Texte sein; Zahlen steuern in Fluent die Mehrzahl.
4. `python3 tools/check_i18n.py` ausführen.

```ftl
# de/gui.ftl
status-tree-summary = { $n } Datei(en) · { $dirs } Ordner
# en/gui.ftl
status-tree-summary = { $n ->
    [one] 1 file
   *[other] { $n } files
 } · { $dirs ->
    [one] 1 folder
   *[other] { $dirs } folders
 }
```

Hinweise zu Fluent: Führende Leerzeichen eines Werts gehen verloren (Leerzeichen im Code davor setzen); zusammengesetzte Texte besser als **einen** Schlüssel mit Parametern schreiben als aus Bruchstücken zusammenzusetzen, weil die Wortstellung je Sprache verschieden ist.

## Zahlen

`vc_i18n::num(x, stellen)` formatiert eine Zahl je Sprache (Deutsch Komma, Englisch Punkt; keine Tausendertrennung). **Hex und Adressen bleiben unverändert** und gehören nicht dorthin.

## Sprachwahl und Erkennung

- Einstellung **Einstellungen ▸ Allgemein ▸ Sprache** (Automatisch / Deutsch / English), gespeichert in der Einstellungsdatei der IDE (`"language": "de"`; fehlt der Schlüssel, gilt „Automatisch“; ältere Versionen ignorieren ihn). Der Wechsel wirkt sofort; die Menüleiste des Systems (macOS) wird neu aufgebaut.
- Erste Seite des Einrichtungsassistenten („Willkommen / Welcome“) enthält dieselbe Wahl. **Bewusste Abweichung** vom Grundsatz des Assistenten „nur ändern, was du am Ende bestätigst“: Die Sprachwahl dort wird **sofort gespeichert**, weil sie sofort wirkt; „Abbrechen“ stellt sie nicht zurück (Entscheidung des Inhabers).
- **Automatisch** erkennt: macOS die bevorzugte Sprache des Systems, Windows die Benutzer-Oberflächensprache, sonst `LC_ALL`, `LC_MESSAGES`, `LANGUAGE`, `LANG` (in dieser Reihenfolge). Deutsch ergibt Deutsch, alles andere Englisch.
- `VC_LANG=de|en|xx` überstimmt alles (Tests, Support, Bilder). `vcc --lang de|en` gilt für einen Aufruf; die Meldungen von `vcc` folgen in Etappe I2, bis dahin wirkt die Option nur als Gerüst.
- **Pseudo-Sprache**: `VC_LANG=xx vintagecoder` zeigt die umgestellten Texte verfremdet (`[Šáñ…~~]`, etwa 40 % länger, Parameterwerte unverändert); alles, was **normal** aussieht, steht noch fest im Code oder fehlt im Katalog.
- Protokollzeilen entstehen in der Sprache, die beim Schreiben galt; nach einem Wechsel bleibt Älteres unverändert.

## Tests

- Einheitentests: `cargo test -p vc-i18n` (Rückfall, Mehrzahl, Parameter, Pseudo-Sprache, Erkennung, `VC_LANG`).
- Die Oberflächentests laufen mit **Deutsch** (im Testlauf gilt „Automatisch“ als Deutsch, solange `VC_LANG` fehlt) und setzen die Sprache nur für den Test-Thread (`vc_i18n::set_thread_language`), damit parallele Tests einander nicht stören. Ein Test, der die Sprache wechselt, geht über `Msg::Set(SetAkt::Sprache(..))`.
- `python3 tools/check_i18n.py` (läuft auch in `release.py check` und der lokalen CI): jeder Schlüssel im Code steht in de **und** en; beide haben dieselben Parameter; jeder `t!`-Aufruf übergibt genau die Parameter des Schlüssels; kein Schlüssel bleibt ungenutzt; keine Umlaute im Englischen außer in den Eigennamen aus `tools/i18n_names.txt`.
- `python3 tools/check_schreibweise.py` kennt Verbotswörter je Sprache (Liste `SPRACHREGELN` im Werkzeug).

## Umstellen und Prüfen (Etappe I1)

- `tools/i18n_extract.py scan|apply|refs|todo`: findet deutsche Zeichenketten im Rust-Code und ersetzt sie durch `t!`-Aufrufe (Schlüssel aus dem Text, benannte Parameter, Kommentar `# Kontext:`); `todo` listet die Schlüssel, die noch keinen englischen Text haben. Nach jedem Lauf `cargo build`, Typfehler (`&str` gegen `String`) mit `tools/i18n_fixborrow.py` oder von Hand beheben und `check_i18n.py` laufen lassen. Das Werkzeug ersetzt nur, was es sicher als Anzeigetext erkennt; Einzelwörter und Texte als Funktionsargumente müssen von Hand geprüft werden (die Prüfung auf feste deutsche Texte findet sie).
- **Tabellen mit festen Texten** (`SystemInfo`, `StudioDef`, Seiten- und Rollenlisten) behalten die deutsche Kennung als Rückfall; angezeigt wird über eine Methode (`name()`, `title()`, `seite_titel()` …), die `t!` aufruft.
- **Befehle** (`BEFEHLE`) und Untermenüs: Schlüssel `cmd-<id>` und `submenu-<slug>`; die Prüfung kontrolliert sie gegen die Tabelle. Alt-Kürzel der Menüs sind der erste noch freie Buchstabe des übersetzten Titels (`befehle::menue_buchstaben`), ein Test prüft die Eindeutigkeit je Sprache.
- **Was nicht übersetzt wird:** Dateinamen und Vorgaben („neu.asm“), Vergleichsmuster, Ausgabedateien von `vcc` und der Bau (bleiben sprachunabhängig), Nutzerdaten (Namen in Projekten), der Text der Mail an den Entwickler (Feldnamen deutsch). Daten (Vorlagen, Emulator-Katalog, ROM-Hinweise) folgen in I3, Meldungen von `vcc` in I2, Hilfe in I4, Handbuch und Bilder in I5.
- **Pseudo-Sprache `xx` als Test:** `cargo test -p vc-gui xx_zeigt` rendert die Kernansichten (Studios, Einstellungen, Assistent, Palette, Dialoge) in `xx` und schlägt bei jedem Rest ohne `[…]` fehl; erlaubte Reste (Eigennamen, Nutzerdaten, Daten aus I3) stehen mit Grund in der Testdatei. `cargo test -p vc-gui layout_pruefung_englisch_und_pseudo_sprache` prüft das Layout in en und xx (bekannte Befunde in `crates/vc-gui/tests/layout_bekannt_<sprache>.txt`; für xx mit 40 % längeren Texten sind es viele, für en keine).
- **Prüfblock:** `python3 tools/i18n_pruefblock.py` schreibt `docs/i18n-pruefblock-oberflaeche.md` (de|en der Kernbereiche) neu; Korrekturen kommen in `catalog/en/*.ftl`, danach den Prüfblock neu erzeugen.
- **Nachweisbilder:** `cargo test -p vc-gui bild_i18n_i1 -- --ignored` schreibt `build/i18n-i1/<ansicht>-<de|en|xx>.png`.
- Ein bereits geschriebener Text (Protokollzeile, Statuszeile) bleibt in der Sprache seiner Entstehung; die erste Zeile „Bereit“ des Protokolls ist so ein Verlaufseintrag.

## Meldungen (Etappe I2)

- **`Diagnostic`** (`vc-core`) trägt `code` (stabil), `key` (Katalogschlüssel `diag-<crate>-<code>[-<variante>]`, `<crate>` = `asm`, `basic`, `ide`; wegen mehrfach vergebener Codes und mehrerer Texte je Code genügt `diag-<code>` nicht), `args` (benannt), `range` und `message` (Text in der Sprache beim Entstehen). `Diagnostic::text_in(lang)` bildet den Text neu, `to_json(lang)` liefert alles maschinenlesbar.
- **`vc_core::Msg`** und das Makro `msg!("schlüssel", name = wert)` bilden Meldung aus Schlüssel und Parametern; ein Parameter kann selbst eine `Msg` sein (verschachtelt). Zwischenschichten der Übersetzer liefern `Result<_, Msg>`. `Msg::raw(text)` (Schlüssel `diag-text`) ist nur für fertigen Fremdtext (Dateisystemfehler anderer Crates) gedacht.
- **Texte ohne Code** (Medien, Disk, Emulatoren, `vcc`, Sprachserver) sind `t!`-Texte (`media-…`, `disk-…`, `emu-…`, `cli-…`, `lsp-…`) und entstehen in der Sprache beim Entstehen.
- **Katalogkommentare** über jedem `diag-`-Eintrag (`# Fehler E204: Kurzbeschreibung`, `# $name: Bedeutung | Beispiel: wert`) erzeugen mit `python3 tools/diag_codes_doc.py` die Liste `docs/diagnostik-codes.md`; `check_i18n.py` prüft Kommentare und Aktualität der Liste. Englische Kataloge tragen keine Übersetzerkommentare (stehen in der deutschen Datei).
- **Sprachserver**: `initialize.locale` (z. B. `en-US`), sonst `VC_LANG`/Systemsprache, Unbekanntes ergibt Englisch; je Serverinstanz, Diagnosen tragen `data: { key, args }`. **`vcc`**: `--lang de|en` > `VC_LANG` > Einstellung/Systemsprache; `--json`-Meldungen enthalten `code`, `key`, `args`.
- Tests prüfen `code`, `key` und `arg_text(…)`; Tests, die Text erwarten, laufen mit Deutsch (Standard ohne Angabe bzw. `VC_LANG=de`).

## Daten (Etappe I3)

- **`vcc`-Hilfe**: `data/cli/en/<befehl>.json` (gleiche Dateinamen und gleicher Aufbau wie `data/cli/<befehl>.json`; Kopfzeile `"i18n": { "status", "source_hash" }`). Technische Felder (`flag`, `short`, `id`, `group`, `aliases`, `choices`, `default`, …) sind in beiden Sprachen gleich; Platzhalter in `usage`, `args[].name` und `options[].value` sind übersetzt. Hilfe, Man-Seiten (`vcc man`), Handbuch-Markdown und Vervollständigungen folgen der Sprache.
- **Alle übrigen Datendateien** (Zielsysteme, Profile, Chips, Emulatoren, ROM-Liste, Einrichtungshinweise, Vorlagen-Listen, Zeichensätze, Zeichen, Emulator-Argumente, Direktiven, MEGA65-Hinweise, BASIC-Schlüsselwörter) bleiben **unverändert deutsch**. Die englischen Texte stehen in **Überlagerungen** `data/i18n/en/<bereich>/<datei>.json`: je Textfeld `"/json-zeiger": { "de": Originaltext, "en": Übersetzung, "status": "maschinell"|"geprüft"|"unverändert" }`. `vc_i18n::localize_json(&mut wert, "bereich/datei.json")` setzt nach dem Laden den englischen Text ein, **nur wenn** an der Stelle noch der Originaltext steht (selbst geänderte Dateien bleiben unberührt) und `en` nicht leer ist. Die Überlagerungen sind in `vc-i18n` eingebettet (`build.rs`). Zwischenspeicher einer Sprache (`OnceLock`) gibt es getrennt für Englisch und alles andere.
- **Vorlagen**: Texte der Projektdateien (Kommentare, Bildschirmtexte) stehen für Englisch in `data/templates/en/<gleicher Pfad>`; der Projekt-Assistent nimmt sie, wenn die Sprache Englisch ist.
- **Neues Feld oder neue Datei**: Textfeld in `TEXT` von `tools/check_i18n_data.py` eintragen, `python3 tools/check_i18n_data.py --erzeugen` legt leere Einträge an, übersetzen, Prüfung ohne Funde. Ändert sich ein deutscher Text, meldet die Prüfung „veraltet“ (Feld `de` anpassen und `en` neu prüfen).
- Prüfung: `python3 tools/check_i18n_data.py` (auch in `tools/release.py check`); Test `alle_ueberlagerungen_passen_zu_ihren_quelldateien` in `vc-i18n`.

## Hilfe (Etappe I4)

- Seiten: `crates/vc-ide/help/en/<datei>.md` (gleiche Dateinamen wie die deutschen). Titel und Gruppennamen stehen in `help/en/_index.json` (`titles`, `groups`); dort auch der Status je Seite (`files`: `status` maschinell|geprüft, `source_hash` der deutschen Seite). `Topic::body_l()`, `title_l()`, `group_l()` liefern die Fassung der aktuellen Sprache, fehlt sie, gilt Deutsch.
- Linkziele (`help:`, `kapitel:`, `bild:`), Codeblock-Anzahl, Tabellenzeilen und Überschriften müssen mit dem Deutschen übereinstimmen (`tools/check_i18n_data.py`). Oberflächennamen auf den Seiten entsprechen den englischen Katalogwerten.
- Erzeugte Seiten (Emulatoren, Befehle, Register, Symbole, „keine Treffer“) kommen aus `catalog/*/help.ftl`; BASIC-Stichwörter aus der Überlagerung `data/i18n/en/help/basic_keywords.json`.
- Handbuchkapitel: siehe unten (I5).

## Handbuch (Etappe I5)

- Kapitel: `docs/handbuch/en/kapitel/<datei>.md` (gleiche Dateinamen wie `docs/handbuch/kapitel`), Glossar `docs/handbuch/en/GLOSSAR.md`. Kopfzeile wie im Deutschen (`id`, `reihenfolge`, `siehe_auch`, `referenz` gleich; `titel`, `stufe`, `zeit` übersetzt) plus `i18n_status` (maschinell|geprüft) und `i18n_quelle` (Hash der deutschen Datei; `python3 tools/check_i18n_data.py --stempeln` setzt ihn). Bilder (`bild:<id>`) sind für beide Sprachen dieselben (zeigen vorerst die deutsche Oberfläche).
- `tools/check_i18n_data.py` prüft Kopfzeile, Linkziele, Codeblöcke, Tabellenzeilen, Überschriften, Listenpunkte, Bilder, deutsche Reste und Aktualität. `help.rs` lädt je Sprache die Kapitel (Test `englisches_handbuch_ist_vollstaendig`).
- Bau: `python3 tools/dokumentation_pdf.py <Repo> <Ausgabe> --lang en` erzeugt `VintageCoder-Handbuch-en.pdf`, `VCASM-Dokumentation-en.pdf` und `markdown-handbuch-en/`, `markdown-vcasm-en/` (Deckblatt, Inhalt, Rechtstext aus der Tabelle `TXT` im Skript; Hinweisblöcke heißen englisch `Tip` und `Caution`).

## Beispiele (Etappe I6)

- `examples/<system>/<projekt>/` bleibt deutsch. Der **Spiegel** `examples/en/<system>/<projekt>/` enthält nur die Dateien mit englischem Text (gleicher Unterpfad): Kommentare, Bildschirmtexte (Zeichenketten), `project.name`/`project.description` der `.vcprj`, Testnamen der `.vctest`, README. Beim Öffnen/Kopieren eines Beispiels in englischer Sprache werden diese Dateien über das deutsche Projekt gelegt (Aufgabe der Oberfläche, `vc-shell/src/start.rs`; im Release-Staging liegt der Spiegel der ausgelieferten Projekte bei, `release.py`).
- **Einstiegsbeispiele** (alles außer Prallball): vollständig; Code zeichengleich, Zeichenketten dürfen abweichen (Ausgabe darf sich dort unterscheiden, der Bau muss gelingen).
- **Große Spiele** (`prallball*`, `troxx`; die Handprüflisten `HANDTEST.md` bleiben deutsch): Programm byte-gleich; im Spiegel nur `.vcprj` und README. Der Kopfkommentar der Hauptdatei steht zweisprachig in der deutschen Datei (englischer Block unter dem deutschen, nur Kommentarzeilen). Das Diskettenabbild kann sich im Etikett unterscheiden (Projektname).
- Werkzeug `tools/examples_en.py`: `anlegen` (Kopien der Dateien mit deutschem Text), `pruefen` (Code gleich, nur Kommentare/Zeichenketten/Felder abweichend, keine deutschen Reste, VIC-20), `bauen` (deutsch und englisch bauen, Ausgaben vergleichen); `pruefen` läuft in `release.py check`. Erzeugte Dateien (`music.inc`, `demo.inc`, `data_*.inc`) sind im Spiegel Kopien; nach dem Neuerzeugen aus dem Generator anpassen.
- Offen: Die Bildschirmtexte von `jumprun` (Zahlencodes in `lib/levels.inc`) bleiben deutsch, bis die Generatoren sie als Zeichenketten erzeugen.
