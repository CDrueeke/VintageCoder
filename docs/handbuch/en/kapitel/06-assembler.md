# Assembler (VCASM) for beginners

**Goal:** You write your first own machine program. You understand what parts an assembler line is made of, use labels, constants, data tables, a macro and the system library, and can read an error message from the assembler.

## What you need

- A C64 project with the assembler template (see [Your first project](kapitel:erstes-projekt)). You replace the content of `src/c64/main.asm` step by step with the examples in this chapter.
- No prior knowledge of assembly language. You only need the will to learn a few things about the processor. They are in the next section.

## What is an assembler?

A processor understands only numbers. A **machine program** is a long series of such numbers. Because nobody wants to type rows of numbers, people write **assembly language**: readable short codes like `lda #2`, which the **assembler** (the translator program) turns into the numbers. VintageCoder has its own assembler for this, called **VCASM**. It handles the 6502 family: the 6510 of the C64, the 8502 of the C128, the 7501 of the Plus/4, the "Sally" of the Atari and the 45GS02 of the MEGA65.

You need to know three things about the processor:

- **Registers:** The processor has only a few memory cells of its own, each holding one byte (a number from 0 to 255). The three most important are called **A** (accumulator, the working register), **X** and **Y** (index registers, often used as counters).
- **Memory:** The computer has 65536 memory cells (bytes), each with an **address**. You write addresses in **hexadecimal** (numbers to base 16, digits 0-9 and a-f) with a `$` in front: `$d020` is the address of the border color of the C64. So a `$` in front of a number means "hexadecimal", `%` means binary, nothing in front means decimal.
- **Chips:** You control picture, sound and input by writing numbers to certain addresses. The basic pattern is: `lda #number` (load a number into A), then `sta address` (store A at the address).

## My first program

In the chapter [Your first project](kapitel:erstes-projekt) you built a program that colors the border red. Now we extend it with a greeting on the screen.

1. Open `src/c64/main.asm` and replace the content with:

```asm
; My first program: red border and a greeting on the screen
.target c64
.basicstub start            ; BASIC line "10 SYS 2061", so that RUN starts the program

start:  lda #2              ; 2 = color red
        sta $d020           ; set the border color
        ldx #0
loop:   lda text,x          ; get one character ...
        sta $0400,x         ; ... and write it to screen memory
        inx
        cpx #5              ; five characters copied?
        bne loop            ; no: continue
        rts                 ; back to BASIC

text:   .screencode "hallo"     ; text as screen codes
```

2. Press **F5** (Run start program; with the template, `main.asm` is the start program). The emulator starts, the border turns red, and "HALLO" appears at the top left.

*[Bild folgt in E13: asm-erstes-programm]*

Line by line:

| Line | Meaning |
|---|---|
| `; ...` | **Comment** up to the end of the line. The assembler ignores it. `//` also works. |
| `.target c64` | This program is for the C64. The IDE uses it to detect the target system. |
| `.basicstub start` | creates the BASIC line `10 SYS 2061`. The C64 runs it on `RUN` and so jumps to `start`. The stub starts automatically at the BASIC start address `$0801`. |
| `start:` | a **label**: a name for the address at this place. |
| `lda #2` | load the number 2 into A. The `#` means: "the number itself", not "the content of address 2". |
| `sta $d020` | store A at address `$d020`, the register of the border color. |
| `ldx #0` | load 0 into X. |
| `lda text,x` | load the byte at the address `text + X`. |
| `sta $0400,x` | write it to `$0400 + X`. Screen memory starts there. |
| `inx` | increase X by 1. |
| `cpx #5` | compare X with 5. |
| `bne loop` | if X is not equal to 5, jump back to `loop`. |
| `rts` | end the program and return to BASIC. |
| `.screencode "hallo"` | stores the five letters as **screen codes**. These are the numbers that screen memory expects. |

> **Info:** `.screencode` and `.petscii` turn text into the matching character codes. The screen of the C64 uses different codes than the keyboard (PETSCII). You find more in the help page [Assembler: text and character sets](hilfe:asm-text).

### Reading the listing

When you build, several files are created in the folder `build/`. The interesting one is the **listing** (`.lst`): on the left the address, then the generated bytes, on the right your text.

```
080d  a9 02             5  start:  lda #2
080f  8d 20 d0          6          sta $d020
0812  a2 00             7          ldx #0
0814  bd 20 08          8  loop:   lda text,x
```

You see that `lda #2` became the two bytes `a9 02`. `sta $d020` became `8d 20 d0`: the command `8d`, then the address with the low byte first. And `text` was replaced by the address `$0820`, which the assembler worked out by itself. How to open the listing in the editor is described in the chapter [Build and run](kapitel:bauen-starten).

## How a line is built

A line has at most four parts: **label**, **instruction** (or **directive**), **operand** and **comment**.

```asm
.target c64
.basicstub start

start:  lda #$00        ; label with a colon
        sta vic2.border ; chip register as a name
.loop:  dex             ; local label is valid until the next global one
        bne .loop
        rts
```

- **Label:** a name with a **colon** at the start of the line. Without a colon, the assembler takes the word for an instruction and reports an error.
- **Instruction:** a short code of the processor (`lda`, `sta`, `jmp` ...). Upper or lower case does not matter.
- **Directive:** starts with a period and is an instruction **to the assembler**, not a command for the processor (for example `.target`, `.org`, `.byte`).
- **Comment:** `;` or `//` up to the end of the line.
- A line holds only **one** instruction.
- Chip registers are available as `chip.register`, for example `vic2.border` instead of `$d020`. If you rest the mouse over the word for a moment, the description appears (see [The code editor](kapitel:editor)).

### Labels

A label is a name for an address. Instead of `jmp $c012` you write `jmp start`.

- A **global** label (`start:`) exists only once in the program.
- A **local** label starts with a period (`.loop:`) and belongs to the last global label before it. So each routine can have its own `.loop` without getting in the way of the others.
- **Anonymous** labels are a single `-` or `+` at the start of the line. In the operand, `-` jumps to the previous `-`, `+` to the next `+`:

```asm
.target c64
.basicstub start

start:  ldx #3
-       dex
        bne -               ; back to the "-" above
        rts
```

Which kind do you use? Anonymous labels for jumps over two or three lines. Local labels for loops inside a routine. Global labels for entry points that are jumped to from elsewhere.

## Addressing in short

For the operand, the way you write it matters:

| Notation | Name | Meaning |
|---|---|---|
| `#$12` | immediate | the number itself |
| `$12` | zero page | address in the first 256 bytes (shorter and faster) |
| `$1234` | absolute | any 16-bit address |
| `$1234,x` and `$1234,y` | indexed | address plus register X or Y |

More kinds are in the cheat sheet of the help [Assembler](hilfe:assembler). You only need them later.

## Constants and data tables

With `.const` you give a number a name. So the meaning stands in the source code and not only the number:

```asm
; Color the border and the background
.target c64
.basicstub start

.const COLOR = 6            ; constant: 6 = blue

start:  lda #COLOR
        sta vic2.border     ; chip register as a name
        sta $d021           ; same effect, but with an address
        rts
```

With `.byte` you store a **table** of fixed numbers in the program. This program gets four colors one after the other from a table and colors the border with them:

```asm
; Get the border color from a table, one after the other (only the last result stays visible)
.target c64
.basicstub start

start:  ldx #0
.next:  lda colors,x        ; color no. X from the table
        sta $d020
        inx
        cpx #4              ; four colors done?
        bne .next
        rts

colors: .byte 2, 5, 6, 7    ; red, green, blue, yellow
```

> **Info:** The processor is so fast that you do not see the first three colors. Only the last one (yellow) stays visible. The point of the example is the pattern: a counter in X and a table that you read with `lda table,x`.

The most important directives at a glance:

| Directive | Effect |
|---|---|
| `.target c64` | target system of the program |
| `.org $0801` | the following bytes start at this address |
| `.basicstub label` | BASIC line `SYS ...`, so that `RUN` starts the program |
| `.const NAME = value` | names a number |
| `.byte a, b, c` | stores single bytes |
| `.word a, b` | stores 16-bit numbers (low byte first) |
| `.screencode "text"` | text as screen codes |
| `.petscii "text"` | text as PETSCII (with control characters like `{clr}`) |
| `.include "file.asm"` | includes a source file |
| `.include "graphics/hero.vcsprite"` | includes a medium (sprite, character set, song ...), see below |
| `.incbin "file.bin"` | includes a binary file |

> **Tip:** Paths in `.include` and `.incbin` are relative to the file that contains the line, and you write them with `/`. [The code editor](kapitel:editor) sums up which lines you can write.

> **Included files:** A file that another source file includes is checked by the editor in the context of that file (preferably the start program) and with the text that is not saved yet. So labels, constants and macros of the including file count as known there, and the address column is also correct in the included file. Errors of the including file appear in its own file. A library file that nobody includes shows missing symbols only as a hint.

All directives are in the help pages [Assembler: directives](hilfe:asm-directives) and [Assembler: cheat sheet and error codes](hilfe:asm-index).

## Including media: sprites, character sets and songs

You draw graphics and compose songs in the editors (see [Graphics and sound overview](kapitel:grafik-ueberblick)); they are in the project as a **media file**, for example `graphics/hero.vcsprite`. In your source text, you include them with the name of the media file, just like a source file:

```asm
.target c64
.basicstub start

.include "graphics/hero.vcsprite"   ; the sprite from the project

start:  rts
```

The assembler treats the medium as a **virtual file**: When including it, it turns it into assembler text by itself (data, labels and constants; for sprites with animations, the tables follow in the same text). You do not have to export anything first, and the source text has no path into the folder `build/`. The file extensions of the editors apply: `.vcsprite`, `.vcpmg`, `.vcchar`, `.vcscreen`, `.vctiles`, `.vcpal`, `.vcsong` and `.vcplay`.

- **Also with `#include`.** `#include "graphics/hero.vcsprite"` includes the medium as well, but only once. With `as name` (`.include "graphics/hero.vcsprite" as hero`), the names of the medium are in a namespace of their own that you reach with `hero.name`.
- **Always up to date.** If the media file changes, the text is created again at the next build. The check in the editor also knows the names of the medium; it does not store anything in your project folder.
- **Readable copy.** After building, you find the generated text to read under `build/.media-cache/` (`<name>.asm`). You can delete the folder at any time; it only speeds up the build.
- **Matching target system.** A medium belongs to a target system. If it does not match the target of the build, the assembler reports the error **E219** with the reason, for example "Medium graphics/hero.vcsprite is for c64, the target of the build is atari8".
- **Old paths.** Earlier projects include `build/export/hero.asm`. This keeps working, but the assembler warns (**W208**) and names the line that you write instead. On the command line, `vcc migrate includes` converts a whole project (without `--apply`, the command only shows what would change).

*[Bild folgt in E13: include-eingefuegt]*

> **Info:** From BASIC, you include media with `#include` as `DATA` lines (see [BASIC in the IDE](kapitel:basic)). If you need a different format or a fixed address, you export the medium by hand in the editor (see [Graphics and sound overview](kapitel:grafik-ueberblick)).

## Assembler in a BASIC program: `#asm`

The reverse way works too: A BASIC program includes machine code with the line `#asm "file.asm"`, which the assembler translates on the way (optionally with `with "song.asm"` for a song as well). In BASIC, you call the code through its labels, written as `asm.name`, for example `SYS asm.start`. The detailed description is in the chapter [BASIC in the IDE](kapitel:basic). The earlier spelling `#blob` does not exist any more; the translator then reports the error B177 with a note about `#asm`.

## Macros: short forms for several lines

A **macro** is a named short form for several lines. At each call, the assembler inserts the text of the macro, as if you had typed it yourself:

```asm
; A macro sets the border and background color
.target c64
.basicstub start

.macro color(c)
        lda #c
        sta $d020
        sta $d021
.endmacro

start:  color(0)
        color(6)
        rts
```

The macro is called `color` and has one **parameter** `c`. For the call `color(6)`, every `c` is replaced by `6`. The listing shows what comes out: at each call, the three instructions appear again in the program.

> **Caution:** A macro is **not a subroutine**. There is no `jsr` or `rts` for it: The code appears again in the program at each call. This is fast, but costs memory. You find more about macros, scopes and structures in the help page [Assembler: labels, macros, scopes, structures](hilfe:asm-macros).

## The system library: names instead of addresses

Instead of remembering addresses like `$d020`, you include ready-made lists of names. With `#include <path>` you get them from the **system library** of the IDE (folder `data/sys/`):

```asm
; System library: names instead of addresses
.target c64
#include <c64/hardware.asm>
#include <c64/kernal.asm>
.basicstub start

start:  lda #COL_GREEN
        sta VIC_BORDERCOLOR     ; border green
        ldx #0
.next:  lda text,x              ; next character
        beq .done               ; 0 = end of the text
        jsr CHROUT              ; KERNAL: print a character
        inx
        bne .next
.done:  rts

text:   .textnull "{clr}hallo welt{ret}"
```

Here `COL_GREEN` and `VIC_BORDERCOLOR` come from `c64/hardware.asm`. `CHROUT` is a routine of the C64 operating system (**KERNAL**) that prints a character on the screen; its name comes from `c64/kernal.asm`. `jsr` calls a subroutine. `.textnull` stores a text and adds a zero byte as an end mark. The loop reads the text until it meets this zero.

For other systems there are matching files, for example `atari8bit/antic.asm` or `mega65/hardware.asm`. The list of all files is in the help page [Assembler: system library](hilfe:asm-library).

## Reading error messages

The assembler reports errors in the **Problems** tab of the tray below the editor and in the editor as an underlined place (see [The code editor](kapitel:editor)). A message always has the same form: error code, description, file and line, plus the affected line. Three common ones:

**Unknown symbol** (E202): You use a label that does not exist.

```asm
.target c64
.basicstub start
start:  lda #2
        sta $d020
        jmp ende
```

```text
error[E202]: unknown symbol 'ende' in 'ende'
  --> fehler.asm:5
```

Solution: The label `ende:` is missing or misspelled. Also watch the upper and lower case; for labels it counts.

**Unknown instruction** (E205): The word is not an instruction. Did you make a typo (`rtz` instead of `rts`) or **forget the colon** on a label (`loop jmp loop`)? Then the assembler takes `loop` for an instruction:

```text
error[E205]: unknown instruction 'LOOP'
```

**Value outside the range** (E203): A byte only fits from 0 to 255.

```asm
start:  lda #300
```

```text
error[E203]: value 300 outside -128..255
```

A click on the message in the **Problems** tab jumps to the line. All error codes are explained in the [cheat sheet](hilfe:asm-index).

## Common stumbling blocks

- **A label without a colon.** `loop jmp loop` does not work; it must be `loop: jmp loop` (E205).
- **Forgotten `#`.** `lda 2` loads the **content of address 2**, not the number 2. For the number itself, write `lda #2`.
- **Upper/lower case in labels.** `Start` and `start` are different names. Instructions and directives are free of this.
- **Several instructions in one line.** This does not work; each line has exactly one instruction.
- **The program does not return.** Without `rts` at the end, the processor runs into the next memory and crashes. An endless loop like `ende: jmp ende` stops the program in a controlled way.
- **Text appears as gibberish.** Screen memory expects screen codes (`.screencode`), output through `CHROUT` expects PETSCII (`.petscii` or `.textnull`).
- **Old names in source code from elsewhere.** Earlier spellings like `.screen`, `.pseudopc`, `.rta` or `.next` still work and give the same bytes; in the editor, a quick fix replaces them with the new name. Two traps: `.long` stores **four** bytes here (often three in other assemblers), and `.align n` fills up, while `.align n, skip` jumps (earlier `.page`). `.petscii` and `.atascii` work on every target, even where the operating system does not know the encoding; the assembler does not report this.
- **The border does not change.** Check whether the program really runs: In the emulator, type `RUN` if the C64 stands at "READY.".
